# 通用插件平台与插件间通信

状态：2026-10-28 目标设计与后续扩展。通用工具、设置、字体和后端契约通信首版已实现；实际接口及边界以 [SDK](plugin-sdk.md) 和 [实施记录](plugin-platform-implementation.md) 为准。下文保留设计意图，草案签名不作为现行 API。

## 目标与边界

业务功能通过插件提供。一个作者应能在独立仓库编写、构建和发布插件，安装后提供自己的入口、页面、后台能力及公开服务；使用已有扩展点时无需修改宿主、添加业务白名单或重新构建整个 WebNav。另一个作者可以只依赖公开契约使用这些能力。

框架仍会演进：出现新的通用扩展位置、平台接口或不兼容协议时，需要发布新版 SDK/宿主；这与每增加一个具体业务都修改框架不同。不得承诺任何未来需求都无需升级宿主。

“一切皆插件”以业务功能插件化为目标，保留最小可信内核：

| 层次 | 责任 |
| --- | --- |
| 必需内核 | 插件发现/装配、依赖与契约注册表、权限/身份、凭据保护、数据基础设施、业务 WS 路由、作用域与资源管理、应用外壳及错误边界 |
| 随附功能插件 | SSH、桌面、任务管理器、文件管理、收藏、同步、主题等业务，按迁移计划使用公共扩展接口 |
| 外部功能插件 | 独立作者发布的工具、协议、服务和视图，与随附功能使用相同公共接口 |
| SDK/契约包 | 可独立使用的类型、运行时校验与示例；不要求作者导入宿主实现类 |

内核负责装配与保护，不处理每个工具的业务。内核可以按模块组织，但插件加载器、鉴权、凭据保护等必需能力不能像普通工具一样被任意卸载或替换。来源不同不应产生某个业务才能使用的私有入口；特权能力仍需要单独声明和授权。

## 插件能够贡献什么

插件清单描述其贡献和依赖，激活时通过所属作用域完成注册。声明、实际注册和运行状态必须同时有效。

| 扩展能力 | 作者负责 | 框架负责 |
| --- | --- | --- |
| 工具页面 | 名称、图标、页面组件、内部交互 | 左侧工具入口、通用标签、可见/关闭状态、错误展示 |
| 插件设置 | 可选声明式字段或自定义配置页面、字体名称与分组 | 已安装总览的设置入口、统一配置页面与保存状态，见[插件配置方案](plugin-settings.md) |
| 命令 | 命令处理器、可用条件 | 受支持位置的展示、打开和执行入口 |
| 连接器 | 协议配置、连接实现、展示组件 | 已保存目标绑定、工作区承载、会话预算与生命周期 |
| 后端方法 | 输入/输出校验、业务处理与收尾 | 已鉴权 WS 转发、操作身份、期限、并发和资源跟踪 |
| 公开服务 | 有版本的服务契约与实现 | 服务发现、依赖解析、提供者绑定和调用 |
| 状态事件 | 有版本的主题、快照与变更 | 订阅权限、有界分发、版本核对、退订 |
| AI 工具 | 描述、结构、作用域和执行实现 | 现有 MCP 发布、授权、目标绑定与任务规则 |

第一阶段开放 `sidebar.tools`、通用工作区页面和[插件总览/可选配置页](plugin-settings.md)，并建立服务调用与事件订阅；命令及连接器视图使用同一机制逐步完善。配置页同时支持总览和插件自身按钮打开，停用或待配置插件也能进行基础配置。字体设置明确展示“插件名称 + 字体名称”。表中目标能力不等于这些扩展点已全部实现。

工具入口继续采用 `contributes.tools` 与 `registerTool` 提案。宿主只理解声明结构，不出现 `if (pluginId === '某个工具')`；插件不能用 DOM 选择器插入、删除或覆盖宿主控件。设置入口与插件详情的“打开”动作也应由贡献声明生成。

## 两种通信方式

### 服务调用：请求一个明确结果

例如系统优化插件需要确认某个启动项关联的程序是否正在运行，可以调用任务管理器公开的只读查询能力，而不是复制采集器、查询另一插件的数据库或访问其私有对象。

公开服务使用具有所有者的命名空间与契约版本，例如 `webnav.task-manager.processes@1`。一个插件可以新增自己的服务契约，不必往宿主 `serviceCapabilities` 增加业务名称。现有 `service:*` 固定槽继续表示宿主稳定服务的替换，新增通用服务注册与其区分，并通过兼容适配逐步迁移。

建议的接口职责如下，最终签名在实现与契约测试时冻结：

| 草案接口 | 职责 |
| --- | --- |
| `api.services.provide(contract, handlers)` | 按声明注册本插件拥有或获准实现的契约，返回幂等注销函数 |
| `api.services.resolve(requirement)` | 按依赖、版本和用户选择解析实际可用提供者，返回受管理的引用 |
| `service.call(method, input, options)` | 发起有期限、身份、目标及操作语义的调用；不返回原始实现对象 |

调用规则：

- 契约规定方法、输入/输出结构、只读/写入/收尾语义及错误码；边界执行运行时校验，传递序列化数据，不共享可变实例。
- 宿主确定真实调用插件、用户/AI 身份与目标范围，调用方不能自行填写 owner 冒充其他会话。授权不会因为调用了另一个插件而扩大；提供者还要核对所属目标与资源。
- 浏览器仍使用每页已有业务 WS。前端不能直接获得后端服务对象；跨插件调用经宿主路由和声明的可见范围，不自行开放 REST 或服务端口。
- 有界并发、消息大小、调用深度及总截止时间由框架统一约束。超时只意味着调用结果未知；取消是合作式通知，不能承诺已停止副作用。
- 写入保留请求 ID、操作 ID、实际提供者和目标身份；跨插件调用传播稳定操作上下文，同一操作重试不得悄悄切换到另一提供者。持久副作用按现有规则保存结果并供查询，不自动重放未知写入。
- 方法执行期间持有对应运行代次的资源引用；长任务另有任务句柄和租约。页面关闭、调用结束与后台任务结束分别处理。

### 事件订阅：获知状态变化

例如系统优化完成一项设置变更后发布受限的状态事件，已订阅的工具刷新相关状态；事件不携带密码，也不自动触发其他插件执行系统写入。

| 草案接口 | 职责 |
| --- | --- |
| `api.events.publish(topic, payload)` | 发布本插件获准发布、经过契约校验的状态事件 |
| `api.events.subscribe(topic, handler)` | 按声明与授权订阅，返回幂等退订函数并自动绑定插件作用域 |

事件主题具有所有者、结构和版本。默认仅在允许的插件后端范围分发；广播到浏览器或 AI 必须显式允许且继续按会话/目标鉴权，不把内部总线自动变成公开订阅出口。

状态主题订阅时返回一致快照及版本，后续变更按版本核对；断线、提供者代次切换或版本缺口时重新取快照。队列有界，允许合并的状态由契约明确；不能静默丢掉依赖完整顺序的数据。需要可靠执行或审计的动作走有结果、可查询的服务调用，不能依赖“发了一个事件”。事件循环与重复订阅须有防护，插件卸载自动退订。

## 依赖与提供者选择

清单分别声明包依赖和契约依赖：前者限定实际插件版本，后者限定所需能力、兼容版本、必需/可选以及是否指定提供者。安装兼容不代表运行就绪。

- **必需依赖缺失：** 插件不激活，显示缺失项及解决入口。安装其他插件仍沿用现有确认流程，不能为补依赖静默执行新仓库代码。
- **可选依赖缺失：** 插件可以运行，只关闭相关组合功能；依赖出现或离开时通过受管理状态通知适配。
- **多个提供者：** 显式配置优先，其次是该契约的默认提供者；没有唯一选择时给出明确未决状态，不能按加载顺序碰运气。
- **必需依赖成环：** 激活前阻止并展示依赖链。需要协作的双方应抽取独立契约或通过不形成启动强依赖的可选订阅连接。
- **版本不兼容：** 不把新服务对象硬塞给旧调用者；用兼容适配或并行的契约主版本迁移。实例可以并行提供 v1/v2，但资源与默认选择要明确。
- **依赖停用/更新：** 先计算受影响调用、任务和消费者；等待相关工作结束，阻止新任务，按依赖顺序撤销。不能因为提供者被禁用就强制结束其他插件已持有的用户连接。

默认提供者选择以契约为粒度保存。作者确需多个契约一起切换时显式声明组合约束；不继续默认清掉同一插件所有无关能力的选择。现有整组选择规则通过兼容层迁移，不能静默改写用户配置。

## 生命周期和故障范围

加载顺序为：校验声明与兼容 → 解析依赖 → 暂存注册 → 有期限地导入/激活 → 验证契约 → 提交运行代次 → 公布入口。安装版本、期望配置、后端运行代次和页面实际加载版本分别记录。

前端激活不能阻止目录、鉴权和其他插件就绪。后台模块导入也纳入启动期限；超时后的迟到注册由已撤销作用域拒绝。失败仅影响所属插件和明确依赖它的功能，旧版本可继续提供服务时保留旧版本。

停用与卸载先进入等待状态，已有任务仍能通过明确的收尾方法结束；收尾方法不能申请新工作。结束后按作用域撤销导航、页面、方法、提供者、订阅、定时器及长连接。清理不完整应报告具体未释放资源和待重启状态，不冒充卸载成功。

框架超时和权限接口是合作式插件的运行契约。当前 Node 同进程插件具备本机代码执行权限，不能据此称为恶意代码隔离；也不能把 Promise 超时称为强制终止代码。更强的执行隔离需单独设计并验收。

## 作者交付物与兼容承诺

作者使用可独立发布的 SDK/契约包、开发模板和验证工具，不相对导入 WebNav 的内部类，不复制完整宿主构建。交付已构建前端模块、后端入口、清单、图标、说明和支持的平台。

开发工具检查清单/实际注册一致性、契约结构、依赖、重复 ID、资源路径及发布包内容；提供隔离开发宿主和插件日志，不把样例写入真实目录。模板至少包含一个独立页面和一对服务提供者/消费者，演示调用、订阅、依赖缺失、错误及清理。

SDK、宿主版本、包版本和服务契约版本分别管理。不兼容变更升级对应主版本并提供迁移说明；同主版本内新增可选能力必须有发现与降级方式。文档中的接口必须与自动契约测试一致。

## 实施与验收

1. 修复[审查中的 D1–D5](plugin-framework-audit.md)，建立正常行为回归测试与独立契约定义。
2. 实现工具贡献、通用工作区、动态服务注册、依赖解析、服务调用与事件订阅；沿用现有 Git 安装、WS、资源租约和 MCP，不另建平行的插件管理系统。
3. 迁移任务管理器入口及一项公开只读能力，再逐项迁移其他可选功能；保持现有服务替换兼容，不改变真实连接与持久数据。
4. 发布 SDK/模板与两个独立示例仓库形态的插件，在冻结的宿主构建上验证。随后实施系统优化业务。

验收场景：

- 插件 A 安装后自行出现入口；插件 B 安装后调用 A 的公开服务并订阅状态。增加 B 时宿主源码和产物均不变。
- 没有 A 时 B 明确降级或等待；安装 A 后按依赖重新评估；多提供者选择稳定，版本不兼容可解释。
- A 更新失败仍可继续使用原运行版本；A/B 停用时入口、订阅和资源正确回收，无关插件、目录及已有终端/桌面不重建。
- 写入超时不重放、不切换提供者重试；跨插件调用不能扩大身份/目标授权；更新等待期间允许结束已有任务。
- 用两个不同作者命名空间验证重名隔离，以及恶意/错误声明、迟到结果、依赖环、事件积压和窄屏布局。

上述验收全部完成后，才能宣称通用插件平台与插件间通信已实现。本次只确认并记录设计，不沿用历史测试数量充当新功能验收。
