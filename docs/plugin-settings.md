# 插件总览与插件配置页面

状态：2026-10-28 首版已实现，实际 API 与验证范围见 [SDK](plugin-sdk.md) 和 [实施记录](plugin-platform-implementation.md)。下文保留完整目标；历史内置业务仍按实际迁移范围说明。

## 当前情况与目标

整改前的 [PluginCenter.vue](../frontend/src/components/PluginCenter.vue) 已有“发现插件 / 已安装”切换，但默认进入发现市场。普通 `configFields` 在详情弹窗中生成简单表单；配置同步、MCP、任务管理器的打开按钮各有专用判断。尚无插件自行提供配置页并由统一入口打开的契约。

本次目标是形成一个明确的管理入口：查看已安装内容、核对实际状态、打开功能、进入设置、管理启停与更新。每个插件可以提供自己的配置页面；插件总览和插件自己的设置按钮打开同一页面，宿主无需认识具体插件。

## 总览入口与布局

继续使用现有左侧“插件中心”，右侧展示内容，保留左侧导航、顶部搜索/标签和已有连接。插件中心默认进入“已安装”，另一个页签为“发现插件”。首次无外部插件时仍展示随附功能，并提供安装入口；实际未读取到清单时显示加载或断线状态，不能当成 0 个插件。

建议布局：

```text
现有左侧导航 │ 插件中心                            从 Git 安装  ＋
             │ 已安装  发现插件
             │ 已安装数量   正在运行数量   待处理数量
             │ 搜索插件…                 状态筛选   来源筛选
             │
             │ ┌ 有区分色的标题栏 ──┐  ┌ 有区分色的标题栏 ──┐
             │ │ 图标 任务管理器     │  │ 图标 系统优化       │
             │ │ 内置               │  │ 第三方              │
             │ ├ 浅/深中性内容底色 ─┤  ├ 浅/深中性内容底色 ─┤
             │ │ 当前版本 · 运行中   │  │ 当前版本 · 已停用   │
             │ │ 一行用途或待处理原因│  │ 一行用途或待处理原因│
             │ │ 打开    设置⚙   ⋯ │  │         设置⚙   ⋯ │
             │ └────────────────────┘  └────────────────────┘
```

卡片标题栏与内容区使用不同的语义化背景，字体保持清晰层级。日常操作使用固定尺寸图标按钮，提供“打开任务管理器”“任务管理器设置”等可访问名称和悬停提示，不均分整行。详细介绍、提交号与依赖放入详情，卡片保持少文字。窄屏单列；字号放大时自动增高、换行，操作区不遮挡文字。

| 卡片区域 | 展示内容 |
| --- | --- |
| 标题 | 插件图标、可读名称、来源标记 |
| 状态 | 正在运行、已停用、待配置、等待任务结束、更新未生效等；静态主题显示已安装/已应用，不假装有运行实例 |
| 版本 | 通常显示当前运行版本；安装版本与运行版本不同时同时标出差异 |
| 打开 | 仅对已声明可用工具入口的插件显示；有多个入口时选择对应工具 |
| 设置 | 有插件配置、配置页面或已注册字体等可调整项时显示；纯后台插件也可以有设置 |
| 更多 | 详情、启停、检查更新、回退、卸载等，依据实际能力显示 |

必需内核、随附默认提供者、可选插件分别标明能力；不能给不可独立停用的内核显示一个不可兑现的启停开关。外部包、随附条目和主题的数量应有清晰口径，正在运行数量不包含静态主题。列表由本机安装清单与运行状态驱动，不要求打开总览时先访问市场网络。

## 同一个配置页，两个打开入口

1. 在已安装卡片上点击齿轮，进入该插件配置。
2. 插件在自己设计的工具栏、菜单或按钮中调用公共打开接口，进入同一配置。

默认在右侧通用工作区打开“插件名称 · 设置”标签，顶部继续保留工作台外壳。页面头部始终显示插件图标、完整名称和“设置”；配置很多时由插件内部页签或分组组织。插件可以选择初始分组，例如直接进入“采样与历史”或“字体与外观”。

每个插件每个浏览器页面最多一个设置实例。重复打开聚焦已有标签，两个入口共享同一份未保存草稿，不复制配置组件。返回原工具可切换原标签；没有左下角“返回工作台”，不替换全页，不卸载已有终端。

标签打开本身不占 SSH/桌面连接预算，也不自动启动插件任务。页面打开过程中显示加载与失败状态；失败提供重试及能使用的基础配置，不影响其他标签。框架记忆总览的搜索、筛选和滚动，回到总览时保持位置。

## 可选配置贡献与 SDK 草案

不是每个插件都必须写一张配置页。支持两种方式，使用相同的配置模型：

| 方式 | 适合情况 | 宿主行为 |
| --- | --- | --- |
| 声明式字段 | 开关、数字、选项和文本等简单公开配置 | 根据已校验 schema 自动生成表单，兼容现有 `configFields` |
| 插件自定义页面 | 多页签、复杂规则、图形化配置或特定业务流程 | 挂载插件注册的组件，使用统一的身份、导航、保存状态和离开保护 |

清单已支持可选 `contributes.settings`。第一版每个插件一个根设置页，内部可以有多个分组；避免同时引入多根设置页、嵌套弹窗和任意路由。以下为清单片段，完整必填字段见 SDK 示例：

```json
{
  "contributes": {
    "settings": {
      "id": "main",
      "title": "设置",
      "entry": "ui/settings.js"
    }
  }
}
```

| 公开接口与设计目标 | 行为 |
| --- | --- |
| `api.registerSettingsPage('main', definition)` | 注册清单中声明的设置组件及受支持分组，自动归属当前插件并跟踪清理 |
| `api.openSettings({ section? })` | 打开当前插件的设置页；无须传自己的插件 ID，返回明确的打开或错误结果 |
| 框架内部 `openPluginSettings(pluginId, section?)` | 总览使用的入口，与插件调用进入同一注册表及同一页面实例 |
| 设置上下文 | 提供配置快照、草稿状态、保存/恢复动作、校验错误、权限、运行状态及版本；不暴露其他插件的私有配置 |

`registerSettingsPage` 与 `openSettings` 已实现；精确参数及可用上下文以 [SDK](plugin-sdk.md) 为准，表中的完整上下文能力仍是设计目标。普通插件不能冒用任意 `pluginId` 打开或写入其他插件设置；将来需要跨插件跳转时使用单独的公开导航声明，仅导航不会获得写权限。

`definition` 的组件使用宿主 Vue。总览从声明中知道是否有配置入口，不为生成列表执行每个插件的代码；注册时验证实际组件与声明一致。插件缺少配置贡献且没有自动生成项时隐藏齿轮，不留无效按钮。

简单字段和自定义页面可以共存，但保存同一份配置，不各维护一套默认值或持久存储。旧 `configFields` 自动适配到设置页；复杂插件可以用公共表单组件复用字段与校验。清单、资源白名单、运行时注册、前端 SDK 与插件中心一并扩展，不能仅在列表中增加按钮。

## 停用、待配置与异常插件如何设置

“业务已经运行”不能成为进入设置的前提，否则必填配置缺失时无法完成首次配置。

- 声明式配置可直接由宿主读取已安装的固定提交清单生成；插件停用、依赖缺失或激活失败时仍可使用，保存不自动启用插件。
- 自定义设置使用独立的设置入口与设置作用域，用户主动打开时才加载已确认安装的模块；不运行业务入口 `activate`，不自动连接服务器、启动采集或申请任务资源。
- 设置入口继续使用同一插件装载基础设施、不可变提交资源和清理规则；不是第二套安装系统。作用域只提供配置所需的公开接口；当前同进程代码机制不构成恶意插件隔离。
- 已停用插件的自定义页只能使用可用的配置服务；需要业务运行的“测试连接”等动作显示条件或另行显式操作，不因进入页面悄悄启动业务。
- 安全模式不加载第三方自定义设置代码，只提供宿主可识别的声明式字段、状态及恢复操作。自定义入口出错时，不伪造不存在的可编辑字段。
- 设置资源路径、样式与图标必须在声明中且通过现有鉴权和路径校验；读取安装说明或预览新版本不执行设置模块。

这要求资源查询与注册机制区分“已安装的配置入口”与“正在运行的工具入口”。不能照搬只返回启用插件 `frontend` 的当前 `plugins.assets` 逻辑。

## 配置保存与生效

| 数据 | 保存位置与范围 |
| --- | --- |
| 插件公共业务配置 | 后端按插件 ID 隔离，经业务 WS 校验、版本核对和持久化 |
| 字体及浏览器外观 | 当前浏览器按插件 ID/flag 隔离；遵守现有外观设置范围 |
| 密码、令牌、私钥等秘密 | 专门凭据流程，不进入普通配置 schema、公开响应、日志或浏览器持久存储 |

业务配置默认“修改草稿 → 保存”；关闭、切换分组会丢弃编辑或插件设置被替换时，由统一离开保护提示保存/放弃/继续编辑。普通标签切换若保留页面实例，不反复提示。自定义页通过同一编辑会话上报 dirty 与校验状态，保存按钮不能绕过统一的配置提交机制。

字体等即时预览明确标记“即时生效”，支持单项或本插件恢复默认，不与尚未提交的业务草稿混在一个含糊的“保存”状态里。恢复业务默认值先进入草稿，保存后才改变运行配置。

保存携带插件、配置版本、所编辑的发布版本与操作身份；另一窗口或插件后台已经修改配置时显示冲突并要求重新核对，不覆盖新值。请求超时显示结果待核对，先查询结果，不自动重放写入。配置成功持久化与实际运行是否生效分开展示：立即生效、等待任务结束、需重新加载插件或待重启，不能统一显示“已经生效”。

有运行实例时设置页使用与实际运行版本兼容的契约；停用时使用已安装版本的配置契约。存在安装/运行版本差异时明确提示。页面打开期间更新不静默丢弃草稿；版本变化后原草稿不得直接套到新结构上提交。无业务任务的设置页不能作为无限阻塞后端更新的资源租约，宿主负责保存可保留的非秘密草稿状态和提示重新核对。

关闭设置页只清理设置视图、监听和临时敏感内容；不默认停止插件的后台工作。插件停用后基础配置仍可打开；卸载则撤销设置入口与页面，清除本页敏感数据，已有持久插件数据按现行保留规则处理。

## 字体设置与这套入口的关系

字体仍由插件使用 `registerFontInfo` 注册、通过 `getFontInfo` 读取有效值；默认字号只写在注册信息中，界面实际字号使用读取值或其生成的 CSS 变量。宿主自己的导航、表单和弹窗也注册字体。

**必须显示可读的插件名称和字体名称。** 全局“字体与可读性”按插件分组；插件设置的“字体与外观”区域只展示当前插件，使用同一个注册表和同一份用户覆盖值。例如：

| 插件 | 分组 | 字体名称 | 示例当前值 |
| --- | --- | --- | --- |
| 任务管理器 | 进程列表 | 表格正文 | 16px |
| 任务管理器 | 性能图表 | 坐标刻度 | 14px |
| 工作台 | 导航 | 左侧导航文字 | 16px |

字号仅为方案示例。插件显示名由框架填入，分组、字体中文名称、默认值和可调整范围由插件声明；稳定身份使用插件唯一 ID + flag。每项提供文字预览、当前值和恢复默认。支持从插件设置直接定位其全局字体分组，两个入口不可保存出两份相互矛盾的字号。

总览和主题设置只消费已验证的字体描述，不为列出字体启动插件业务。若字体描述尚未加载，不伪造项目；设置元数据加载与业务激活应分离，使停用插件的可配置描述也能按需取得。插件升级保持 flag 稳定或显式迁移，卸载撤销展示，既有用户覆盖值遵循保留/恢复策略。

## 迁移与验收

实施顺序：

1. 扩展设置贡献、统一配置上下文与独立设置作用域，兼容旧 `configFields`。
2. 将插件中心默认页改为已安装总览，增加通用打开、设置与实际状态展示。
3. 接入字体注册与按插件分组设置，迁移配置同步/MCP 等专用打开逻辑，保留其秘密数据与授权边界。
4. 用一个声明式配置插件和一个自定义配置插件验证；二者都可在自己的页面放置设置按钮，不改宿主业务代码。

验收覆盖：无配置项、仅后台插件、停用/待配置/依赖缺失/激活失败、安全模式、加载失败、重复打开、分组定位、未保存草稿、多窗口版本冲突、未知保存结果、运行版本差异、卸载清理、字体来源标签、深浅色、字号放大和窄屏。任一入口都打开同一编辑实例，旧终端及桌面保持原连接；设置页不能通过打开动作隐式启动任务。

运行验证已补充到[实施记录](plugin-platform-implementation.md)，包括独立插件、停用配置、草稿复用、字号应用、卸载清理与窄屏；不要将全部目标条目等同于本轮已验收。
