# DeepSeek Harness 更新与插件调研

调研日期：2026-10-27。范围是官方 `deepseek-ai/deepseek-harness` 的公开源码与发布文档；没有安装或执行 Harness，也没有验证其生产更新服务器。本文区分上游事实、WebNav 已有实现、本轮修改与后续方案。

## 2. 宿主在线更新如何工作

### 桌面壳负责更新，业务进程负责收尾

Harness Desktop 使用 Electron，业务 Host 是独立子进程。更新由壳内的 `DesktopUpdateCoordinator` 接入 `electron-updater`，并非某个业务插件在运行中覆盖自己。

协调器明确设置 `autoDownload = false`、`autoInstallOnAppQuit = false`、`allowDowngrade = false`。检查只获取候选；下载与安装分别由用户触发，均绑定主进程保存的目标版本。下载/安装期间保持该目标，并发操作复用进行中的 Promise；普通退出不会顺便安装。[协调器源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/apps/desktop/src/update-coordinator.ts)

### 自动检查有节制，下载失败不无限重试

启动后检查，常规基础间隔 10 分钟、±20% 随机抖动，失败指数退避，上限 1 小时，成功重置。使用单调时钟，并从检查结束起安排下一次；前台恢复、系统唤醒共用截止时间，手动检查可立即执行并复用在途请求。[调度源码](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/apps/desktop/src/update-schedule.ts)

下载 HTTP 使用 60 秒无活动超时，持续收到数据时不限制总时长；下载失败保留重试入口，要求用户再次操作。安装前先检查任务，取得必要的中断确认，然后锁住新请求、等已接收请求结束，再检查任务并关闭 Host。任务状态未知、收尾失败或未确认旧 Host 退出，都不继续安装；已确认退出但安装交接失败时，尝试恢复当前版本 Host。[桌面更新行为与验证边界](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/apps/desktop/README.zh.md#updates)

这里的“恢复 Host”不是新版本安装后必定自动回退旧版本。官方文档还将真实安装器、签名、公证、跨版本安装及 CDN 验收区分为独立验证项目，不能根据单元测试推断已经完成所有生产验证。

### 发布链路是在线更新的一部分

发布目录按系统/架构隔离，正式与测试源分开，客户端使用打包时绑定的源。发布前核对构建记录、版本、大小与 SHA-512；先上传安装包和 blockmap，再发布渠道 YAML，保留历史产物。上传记录区分操作意图、回执和最终结果；缺最终结果不等于上传失败。当前部署采用固定 Nightly，不能理解成已经向用户开放稳定/测试频道切换。[发布说明](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/apps/desktop/publishing/README.zh.md)

## 3. 插件系统如何工作

### Cordis + profile + bundle

Harness 与 WebNav 都以 Cordis 装配服务。Harness 的 profile 是独立 npm 项目，组合包通过 `dsh.bundle.patch` 提供配置层，profile 记录有序 bundle 选择与自己的 patch；禁用选择并不删除包。启动器提供包管理运行时，Desktop 随包附带 pnpm，避免依赖用户 PATH 中的 pnpm。[应用装配](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/boot/app-boot/README.zh.md)

安装、启停、卸载共用管理服务，网页和 `plugin_manager` 工具只是不同入口。保存的 `enabled` 不等于成功运行；失败条目仍可见。插件在宿主进程执行，能力声明、版本检查都不是沙箱。官方按需插件跟随运行中的 DSH 版本，开发环境则指向对应源码工作区，不根据当前目录猜安装位置。[rc.3 插件管理](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/boot/plugin-manager/README.zh.md)

### 市场与安装分开

市场服务只读取配置过的索引，校验格式、缓存、分页，并标注兼容性与安装状态。`plugin_market` 是只读发现工具，真正安装仍调用管理器。索引不签名，市场中的名称/版本只是索引声明，实际安装以包清单为准。rc.3 的市场“有更新”不代表已有完整的直接升级操作。[市场服务](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/boot/plugin-market/README.zh.md)

### 热更新有明确边界

HMR 将模块替换、Include 刷新、profile 重组串行协调；包安装在队列外执行。它追踪模块依赖和文件身份，停止受影响 Loader 条目、逐出模块，再重组加载。宿主依赖、Worker 缓存等变化可能要求重启。包重组时替换代码导入/启动失败，旧代码并不保证仍在运行；不要将源码热替换等同于事务回滚。[HMR 实现与限制](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/boot/hmr/README.zh.md)

### 当前主线补了专门的插件升级操作

在固定主线中，`listVersions` 有界查询第三方 registry 包的新版本及兼容性；`updateBundle` 只接受更高的精确版本，先检查兼容。启用 HMR 时先移除旧版再安装新版，新版失败/取消/激活失败则尝试重装旧版，单独返回恢复结果；恢复也失败时会留下未安装状态。没有 HMR 时覆盖安装并提示重启。这部分不能归到已发布 rc.3 上。[主线升级源码](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/boot/plugin-manager/src/index.ts#L665)

## 4. 对 WebNav 的取舍

| 方面 | WebNav 当前基础 | 本次决定 |
| --- | --- | --- |
| 进程管理 | 每用户单实例 supervisor、托盘、重复启动打开已有网页 | 保留并作为整包更新控制层，不引入 Electron |
| 插件来源 | 公开 Git、具体提交、独立版本目录、确认后运行安装步骤 | 保留，不改成运行目录内 `git pull` 或直接覆盖依赖 |
| 热更新 | 暂存注册、稳定服务桥、依赖联动、资源租约、失败时保留旧实例 | 保留；SSH/桌面/AI 长任务比通用模块热重载更需要保护 |
| 运行状态 | 已有 pending 原因、运行 provider、版本目录 | 补充实际运行版本与提交，避免把已安装新版当成已生效 |
| 安装预览 | 已绑定目标提交、用户、有效期 | 补充配置基线版本；其他窗口改变插件设置后必须重新预览 |
| 更新说明 | 已检查兼容与依赖 | 补充分辨同提交、同版本新提交、升级、降级及静态声明差异 |
| AI 接入 | 可选 automation 声明、统一 MCP、权限与任务生命周期 | 保留；未声明的插件正常运行，声明不自动授予 AI 权限 |
| 主程序更新 | 调研时从源码/构建目录启动 | 后续已实现安装包、稳定入口、签名更新和恢复，见 [在线更新](online-updates.md)；正式附件未发布 |

不照搬任意 YAML JavaScript 表达式、Node 内部模块缓存替换、强制更新策略或多 profile 体系。这些没有解决 WebNav 当前单用户本机工作台的必要问题，反而扩大维护范围。

## 5. 本轮已实施

1. 更新预览绑定创建时的插件配置 revision；旧预览即使携带后来读取的最新 revision，也不能继续安装。界面提示重新读取并重新确认。
2. 预览显示安装/升级/同版本代码变化/降级；相同提交明确无需重复安装，不再显示无意义的安装确认。
3. 静态比较能力、AI 工具、依赖、外部组件、安装步骤和热更新声明。这里只比较声明，不分析代码行为，也不替代既有风险确认。
4. 详情分别显示已安装与正在运行的版本和提交；新版本激活失败、等待任务结束等场景不混淆两者。

这些修改没有自动下载/执行插件，也没有改变现有 MCP 授权或活动连接。

验证记录：类型检查与生产构建通过；15 项插件测试覆盖提交绑定、过期确认、版本比较、声明变化、失败时保留旧实现、资源等待及运行版本投影。独立本机数据与 Git 测试仓库的浏览器验收覆盖相同提交、更新差异、旧预览失效及重新确认、在线更新、已安装/运行版本和 390px 布局。没有连接真实远程服务器，也未执行真实 Harness 安装升级或 Windows 开机重启验收。

## 6. 宿主在线更新设计与实施

下述为调研时形成的设计，后续实现已补齐；实际目录、Gitee 普通页面源、签名协议、操作入口与验收以 [在线更新](online-updates.md) 为准。正式附件尚未上传，Windows 注销/重启不属于本轮已验证项目。

### 稳定启动器和独立发布目录

正式版随包提供已验证的 Node、依赖、前端和原生辅助程序。安装目录采用固定启动入口与不可变 `releases/<version>/`，用户数据继续独立保存。登录自启的快捷方式只指向固定入口，不再记录某次源码目录、开发模式或外部 Node 路径。

源码开发模式继续使用现有命令，不受正式版在线更新器覆盖。稳定启动器持有现有单实例锁，读取 `current`/`previous` 指针，启动选定版本。启动器自身升级由独立安装器接管，避免正在运行的控制层自我覆盖。

### 更新状态与请求

提供检查、下载、取消下载、安装、查询状态五类经过鉴权的 WS 操作。候选由控制层保存，网页只提交目标标识和操作 ID，不能指定任意下载地址或可执行命令。状态至少包括：检查中、可更新、下载中、校验中、就绪、等待任务结束、安装中、失败及恢复结果。

后台只检查版本；初始建议每 6 小时 ±20% 抖动、失败退避至 24 小时，手动检查复用同一在途请求。下载失败显示原因并等待手动重试。下载授权与重启安装授权分开，普通退出不自动安装。这些是 WebNav 的建议值，不是上游参数或已完成测量。

### 校验、任务保护与切换

发布方先上传不可变版本包，再发布签名清单。清单约束版本、平台、架构、大小、摘要、最低启动器版本、数据格式兼容范围与包地址；客户端用随包信任公钥验证，并限制解压路径、总大小与文件数量。摘要负责完整性，来源签名负责发布者身份，不能互相替代。

下载到临时目录，校验并暂存完整版本后再允许安装。复用资源租约覆盖网页 SSH/桌面、本地终端、AI 任务、文件写入和配置同步；先停止新任务准入，等待已接收的操作稳定，再复查活动资源。默认等待空闲；用户明确选择结束任务才能继续关闭。状态未知或旧进程未确认退出时停止切换。

旧 worker 退出后原子切换版本指针，新 worker 必须通过带随机令牌的私有 IPC 回报版本及就绪状态，不能凭端口可访问判断成功。启动超时或自检失败只做有界恢复，并展示结果，避免永久重启循环。

### 回退与数据边界

保留上一完整发布包和最小操作日志，用于区分未完成下载、已切换但未就绪、已成功启动。代码回退仅在旧版仍能读取当前数据格式时自动进行。不可逆迁移必须另行规划可核验的备份/迁移/恢复；不能自动用旧数据库覆盖用户更新后的数据，也不能承诺任意版本一键回退。

升级失败恢复代码，不重放 SSH 命令、文件写入或结果未知的 MCP 操作。任务历史与凭据仍在原数据目录，日志仅记录版本、阶段、受控错误码和恢复结果。

### 交付顺序与验收

1. 发布包、稳定入口、自启迁移及精确版本就绪握手。
2. 可信清单、后台检查、下载校验、状态界面与显式安装。
3. 活动资源排空、异常恢复与兼容性受限的代码回退。

验收使用独立本机更新源和临时数据：网络中断、摘要/签名失败、磁盘不足、并发检查、旧确认、任务临界启动、旧进程未退出、新版启动失败、更新中断电模拟、自启失效与重复启动。最后用真实 Windows 安装包完成旧版到新版升级、登录自启、注销/重启验收。未完成这些之前，不将现有托盘启动描述为具备成熟整包在线更新。
