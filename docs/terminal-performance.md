# 终端历史淘汰与持续输出控制

本文补充 [架构方案](architecture.md) 与 [WS 协议](websocket-protocol.md)，规定网页 SSH 终端的内存、渲染和滚动行为。当前仍为设计阶段，下列参数是首版实现及压测的起点，不代表已验证的性能指标。

## 1. 处理原则

持续输出时，只保留有上限的近期终端历史。超过上限的最旧历史由 xterm.js 自动淘汰，不在 Vue 状态、字符串数组或其他组件中重复保存全量输出。

需要分别限制三件事：

| 层次 | 处理方式 | 责任方 |
| --- | --- | --- |
| 已解析的历史行 | `scrollback` 限制数量，滚出上限的最旧行淘汰 | xterm.js 核心 |
| 可见区绘制 | 由终端渲染器更新视口，不为每行历史创建 Vue 节点 | xterm.js；可选 WebGL addon |
| 未解析的字节流 | ACK 额度、发送队列上限和 SSH 读取背压 | 本项目前后端通信层 |

历史按容量淘汰，不按时间 TTL 删除。“离当前视口远”不意味着可以删除较新的输出；用户翻到较早历史时，仍维护最新的有限历史窗口。

终端状态依赖完整的控制序列和字节顺序。只有已经被解析为终端状态的旧历史可以自然淘汰，不能从未解析的 WS 消息中任意删帧或丢失 UTF-8、ANSI 序列的部分字节，也不能定时 `clear()` / `reset()` 来控制内存。正常按额度分块可以跨越字符或控制序列边界，只要按原顺序完整交给 xterm.js，由其保留跨块解析状态。

## 2. 第三方能力与应用职责

- 使用 `@xterm/xterm` 核心的 `scrollback`，无需另装普通列表虚拟滚动插件。终端历史和普通日志行列表的状态模型不同。
- 按需使用 `@xterm/addon-webgl` 加速可见区绘制。初始化失败或 WebGL context 丢失时释放 addon，回退到所选版本支持的内置渲染器；不重建 SSH 会话，不丢失正常终端缓冲。
- WebGL 不替代历史上限、输入解析或 WS 流控。首版不启用图片等额外大资源终端扩展。
- 应用负责跟随最新输出、阅读历史的提示、写入队列计数、通道清理和多终端总量控制。
- 仅使用选定版本公开 API；不修改 xterm.js 私有 buffer、内部循环数组或渲染器字段。

## 3. 首版参数

以下大小使用原始二进制 payload 的字节数，`KiB = 1024 B`、`MiB = 1024 KiB`。

| 配置 | 初始值 | 含义 |
| --- | --- | --- |
| 历史容量 `scrollback` | 2,000 行 | 每个终端的历史行，不含当前屏幕行 |
| 用户可配置历史范围 | 500–10,000 行 | 超界拒绝；修改时提示较旧历史可能被淘汰 |
| 单个终端输出帧 | 最大 16 KiB | 后端按额度切块，控制单次写入大小 |
| 未确认输出窗口 | 256 KiB | 单会话已发送、尚未确认解析的 payload 上限 |
| 单会话应用输出缓冲硬上限 | 1 MiB | 对应用持有的待发块、未完成写入引用和 WS 排队分别计量；保守合计，允许重复计量 |
| 进程/页面应用输出缓冲预算 | 各 8 MiB | 后端与前端分别限制其所有终端的可计量输出缓冲；预算不足时先背压，再拒绝新增会话 |

这些限制针对应用可以计量的队列，不能直接等同于整个 JS 堆、浏览器网络缓存或 GPU 内存上限。历史行的内存还受列宽、Unicode 内容、属性和终端数量影响，必须结合持续输出压测评估整体资源。

这里的“行”是 xterm.js 的缓冲行，不是原始日志条数；长行自动折行和窗口尺寸变化引起的重排会影响可保留的内容范围。

首版还须校验终端尺寸、同时活动会话数量与输入速率，具体上限在脚手架实现时集中配置；扩大历史或会话上限后重新验证资源预算。

## 4. 滚动与阅读行为

### 跟随最新输出

用户位于底部时，继续跟随新输出。由 xterm.js 维护滚动，应用避免在每个消息回调里重复调用 `scrollToBottom()`。

### 向上翻阅

用户向上滚动后，新输出仍正常解析和保存到有限历史中；应用不强制跳回底部。显示轻量的“有新输出 · 回到最新”入口，不为提示维护另一份输出副本，也不声称精确计算所有新增日志行。

可以通过公开的 `buffer.active.viewportY` 与 `baseY` 判断是否在底部，结合滚动事件及解析完成事件更新状态。该行为针对普通 buffer；`vim`、`top` 等使用 alternate buffer 时交由终端自身的屏幕语义处理，不显示普通历史的跟随提示。

### 最旧历史被淘汰

达到 `scrollback` 上限后，即使用户正在阅读历史，也不扩大缓冲无限保留。优先由 xterm.js 保持其仍可保留的阅读位置；当正在查看的最旧内容被淘汰时，视口只能显示仍然保留的内容。

因此不承诺“持续输出期间当前阅读内容永远不变”。在历史视图显示“仅保留最近 2,000 行历史”的提示；支持回到最新，但不提供已淘汰内容的再次加载。需要长期保存日志时由远端工具保存文件。

## 5. 字节流和 ACK

接收链路为：WS 二进制消息 → 有界的写入调度 → `terminal.write(Uint8Array, callback)` → 累计解析确认。无需先将输出解码成字符串再逐行切分。

`write()` 会异步排队，其回调表示这一批数据已由解析器处理，不代表已完成屏幕绘制。ACK 必须依据这个回调，不能在收到 WS 消息时提前确认，也不能依赖 `onRender`、滚动位置或用户是否看到了输出。

每个已绑定的终端通道维护独立的 `sentBytes` 与 `parsedBytes`。客户端通过 `terminal.ack` 发送累计解析字节数，服务端计算 `inFlight = sentBytes - parsedBytes`；发送新帧前保证 `inFlight + payloadBytes <= windowBytes`。

```json
{"v":1,"type":"terminal.ack","parsedBytes":65536}
```

计数只包括终端输出二进制 payload，不包括 WS 帧头、JSON 控制消息或字符数量。累计确认必须是非负安全整数且不得超过已发送字节数；重复或旧确认不重复增加额度。新终端绑定时计数从零开始，禁止跨连接复用 ACK。

额度耗尽时暂停 SSH channel 读取，收到有效 ACK 后继续；控制、resize 和输入消息不被输出额度阻塞。前端可合并相邻小块，但仍遵守帧与队列上限；ACK 初版可每批解析完成后发送，后续合并 ACK 必须保留短尾刷新机制，避免额度永远得不到释放。

后台 tab 或繁忙的主线程可能延迟解析。额度和队列上限必须在此期间仍然有效，不能因为计时器、绘制回调暂停而无限缓存。持续无解析进展或达到硬上限时给出明确错误并释放相应终端，不静默删掉中间字节再继续显示。

SSH 背压可能最终限制远端向该终端输出的进程，这属于有界流控的行为，不保证在本地无限慢时远端仍能无限快地输出。

## 6. Vue 与多标签生命周期

- 用 `markRaw`、`shallowRef` 或组件外的实例管理器保存 Terminal 实例，避免将其内部 buffer 转为 Vue 深层响应式数据。
- Vue 仅维护会话名称、连接状态、当前标签和“有新输出”等少量 UI 状态；输出直接送给 xterm.js，不进入 Pinia 的全量日志数组。
- 切换应用内终端标签保留同一个实例及有限历史。未选中的终端仍按额度解析并确认输出，绘制交给 xterm.js 的可见性处理；不以“不可见”为由缓存原始输出等待切回。
- 浏览器后台节流导致解析变慢时允许背压生效；不能为了持续 ACK 而虚假确认尚未解析的数据。
- 重新显示时测量尺寸并按需刷新视口，不从历史数组重放全部输出。resize 应节流，避免反复触发历史重排。
- 关闭终端时释放 Terminal、addons、事件监听、计时器、ResizeObserver、WS 和所有引用。单纯切换标签不执行关闭逻辑。
- 大量终端同时存在时，历史容量和解析成本会累计；总量限制与会话清理必须独立于单终端 `scrollback`。

## 7. 验证要求

实现阶段优先使用本地模拟输出源，不默认连接真实服务器。需要验证：

1. 连续产生超过历史上限数十倍的输出，普通 buffer 长度维持在历史行数加当前屏幕行数的范围内，没有额外无限增长的应用字符串副本。
2. 大量输出期间滚轮翻阅、复制和“回到最新”可用；被淘汰的历史行为与提示一致，不反复强制跳底。
3. 持续高流量输出时，256 KiB 未确认窗口、各缓冲上限和累计 ACK 校验有效；输入中断命令仍可响应，业务 WS 仍可修改配置。
4. 覆盖跨帧 UTF-8、ANSI 序列、无换行长输出、彩色输出和 alternate buffer，不因历史淘汰或分块导致字符、光标及屏幕状态错误。
5. 多终端、隐藏标签、后台页面、窗口尺寸变化及 WebGL 失败都能保持有限缓冲；恢复可见后状态正确。
6. 关闭并重新打开终端后，实例、监听器、缓冲引用和 WebGL 资源确实释放。持续运行观察内存趋势，区分缓存预热与持续无界增长。

记录测试环境、输出速率、终端数及资源趋势，再决定是否调整默认值。当前文档未宣称已通过这些运行测试。
