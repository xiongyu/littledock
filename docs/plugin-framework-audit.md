# 插件框架审查（2026-10-28）

状态：以下保留 2026-10-28 整改前的审查快照。D1–D5 已修复并转为回归测试；A1 通用工具入口与设置、字体、通信已实现。A2 历史内置服务仍保留固定槽兼容装配。当前结果见[实施记录](plugin-platform-implementation.md)。

## 结论

当前框架实现了**外部代码安装、预留服务替换、固定视图槽替换、主题下载和部分动态扩展**，尚未实现**插件自行声明入口并在工作台打开独立页面**。

“之前的插件都是改框架显示的吗”需要区分两件事：

- 当前 17 个内置条目均没有独立 `frontend` 入口。它们的界面与打开方式由宿主编译、装配；任务管理器、配置同步、AI 接入还有业务专用按钮和分支。按当前路径增加一个全新的工具页面，确实仍要改宿主。
- 外部插件替换已预留的服务和视图、增加命名空间 RPC、注册 AI 工具或下载静态主题，已经可以不改宿主；有现存示例和本次通过的测试。因此不是空壳，但离“独立功能安装后自行出现”的目标有实质缺口。

前一版系统优化设计沿用新增服务白名单和专用视图槽的做法，会继续扩大这个缺口。应先补通用入口和工作区承载，再让系统优化成为独立插件。仅改图或补一个按钮不能解决。

## 架构缺口

### A1 · 高：独立页面注册缺失，入口继续依赖宿主业务分支

`frontend/src/plugins.ts:13,36` 只有 9 个固定视图槽，且 `registerView` 只允许相应默认服务提供者占用；无通用工具、导航、设置动作或工作区页面 API。

`frontend/src/App.vue:68,255,392,522,544` 分别保存任务管理器专用状态、加入标签、处理关闭、渲染左侧按钮和正文；`PluginCenter.vue:165,171,172` 识别 MCP、配置同步和任务管理器来显示专用打开按钮。换成别的新工具还要再增加一组分支。

自定义连接器已经可以注册名称、表单、后端处理器和 `open` 回调，不能说完全不支持新协议。但 `App.vue:466` 仅把打开交给回调；SDK 没有通用工作区挂载 API，后续宿主工作区处理仍列举内置协议。作者需要自行管理展示，无法按公共接口获得统一标签与页面生命周期。

修正方向：采用[通用工具入口提案](plugins.md#通用工具入口提案)，宿主读取插件声明，渲染通用入口、标签和页面；业务功能保留在插件内部。`extension:<name>` 已能承载自有 RPC，不需要给系统优化再增加 `service:systemOptimizer`。

### A2 · 中：内置模块与可管理插件混为一类

`manager.ts:15,43` 的内置列表由固定服务表生成，非扫描插件入口后动态装配。`manager.ts:206` 对内置 ID 仅接受 `select`；隔离调用 17 个内置条目的 `disable` 均返回 `NOT_FOUND`。

此外，`PluginCenter.vue:164` 根据未声明 `reload:restart` 就显示支持热插拔、热更新；该句也出现在内置条目详情，但它们实际没有独立启停/更新路径。可替换默认提供者、启停外部包、升级宿主内置代码是三种不同能力。

修正方向：明确区分宿主必需基础设施、随附的默认提供者、可选功能插件。可选功能逐步使用与外部插件相同的注册/清理流程；确实不能单独禁用的核心能力应在管理界面如实标明，而非给所有条目套相同能力说明。

## 已复现的实现缺陷

### D1 · 高：前端插件挂起会阻塞目录加载及其他插件

位置：`frontend/src/plugins.ts:18–34,64`；`frontend/src/backend.ts:64–72`。

加载队列整体串行；模块导入、`activate` 和每个 `onDispose` 没有期限。一项永不结束，后续插件同步也永不开始。首次目录订阅在 `await loadPlugins()` 之后，因此单个插件初始化挂起还会阻止目录进入 ready 状态。

复现：真实前端加载器在隔离模块环境中运行，使用实际 Vue；一个插件的启动 Promise 被控制保持未完成，后面的健康插件运行次数为 0；另一个用例在清理阶段挂起，同样阻塞随后入队的健康插件。释放测试 Promise 后队列才继续。源码确认不存在超时，并非声称 35ms 是产品超时标准。

修正方向：目录同步不依赖扩展全部启动；导入、激活和清理有明确期限与候选代次，失败隔离到插件；迟到注册不得重新生效。保留旧实现及重试入口，不能用整页刷新作为常规回收方式。

### D2 · 高：后端模块导入绕过启动超时

位置：`backend/src/plugin-system/runtime.ts:99,123`；`backend/src/app.ts:61`。

15 秒限制只包住 `activate(api)`，前面的 `await import(...)` 没有限制。插件模块或其依赖存在未完成的顶层 await，就会卡住本次 reconcile；冷启动的 `createApp` 也在等待它。

复现：合成插件在模块顶层等待测试门闩。等待 15,250ms 后应用初始化仍未完成；释放门闩后正常返回。整个过程只启动隔离本机服务。这里确认的是初始化与插件队列未收尾，不能据此声称 Node 事件循环或所有已有连接都已停止。

修正方向：把导入及激活纳入同一个启动期限，隔离失败单元，防止超时后的迟到代码提交注册。Promise 超时不能强制停止同进程 JavaScript；严格终止第三方代码需要额外执行隔离，不在当前实现中。

### D3 · 中：服务契约检查落后于宿主调用，接受不完整替换

位置：`backend/src/plugin-system/runtime.ts:37,130`；`backend/src/plugins/transport.ts:199–202`。

任务管理器当前宿主会调用 `recordingStatus`、`configureRecording`、`queryHistory`、`historyPoint`，但 v1 必需方法列表与插件文档没有这些方法，也没有在调用前协商可选能力。插件即便完整满足当前公开的旧列表，仍可能被选为正在运行的提供者后，在历史功能请求时失败。

复现：合成提供者实现目前检查的全部方法与 `size/sizeRemote`，实际被成功启用；经已鉴权的业务 WS 创建合成监控，再请求 `taskManager.recordingStatus`，响应为 `INTERNAL`。

修正方向：服务契约从实现类中独立出来；新增必需方法升级契约版本，或声明可选能力并让 UI/调用方降级；运行时校验与公开类型、文档来自同一契约。不能简单不断向同一个 v1 列表追加方法而破坏已发布插件。

核对排除：`sessions.createManaged` 也不在旧必需列表中，但自动化服务会根据提供者与实际方法过滤内置 SSH 工具。没有把它算成已经复现的 AI 调用故障。

### D4 · 中：更新期间允许收尾的 RPC 使用业务白名单，漏掉插件释放动作

位置：`backend/src/plugins/transport.ts:143`；`backend/src/plugin-system/runtime.ts:12`；`backend/src/desktop/update-bridge.ts:43–54`。

维护模式允许的收尾动作依靠固定方法名正则，公共 `registerRpc` 没有声明“仅结束已有任务”的方式。普通 `plugin.<id>.release` 被当成新工作拒绝，而插件的后台租约又计入整包更新等待条件。

复现：通过业务 WS 调用合成插件 `hold`，占用 1 个资源；进入更新等待状态后调用 `release`，返回 `UPDATE_WAITING`，资源仍为 1；同插件的 `status` 正常。退出等待状态后释放成功，资源变为 0。

影响：需要用户从页面主动结束的插件任务可能只能先取消更新再结束，或者依赖插件自行完成；不是所有更新都会永久死锁。

修正方向：给 RPC 定义受约束的读取/新任务/已有任务收尾语义，并绑定目标和权限。维护模式据此放行，收尾处理不得借机申请新资源；不能以添加每个插件的方法名解决。

### D5 · 中：多协议插件的提供者选项串项

位置：`frontend/src/plugins.ts:72`；`frontend/src/components/ServerEditor.vue:96`。

`connectorOptions(type)` 遍历所有注册项，却只检查“该插件是否有目标协议”，没有检查当前注册项是不是该协议。同一插件注册 Alpha、Beta 后，查询 Alpha 的提供者会得到 Alpha 和 Beta，两项还共享同一个 `pluginId` 作为选择值。

复现：实际前端加载器注册两种协议，`connectorOptions('plugin:alpha')` 返回名称 `['Alpha', 'Beta']`。

修正方向：按注册表键中的协议精确筛选，保留明确的协议身份；针对单插件多协议和多插件同协议建立回归测试。

## 已确认有效的部分及其他限制

本次现有插件专项 15 项、MCP 专项 14 项全部通过，覆盖 Git 元数据读取不执行安装脚本、确认绑定提交、平台/依赖检查、安装失败保留旧版、服务替换、静态主题资源、命名空间 RPC、连接器注册、资源租约等待、订阅延续、失败回退、安全模式和自动化声明/授权等。资源等待用例使用隔离本地 PTY，自动化用例使用本机模拟 SSH。

服务白名单本身不是应删除的错误：它限制可以替换的宿主稳定服务，鉴权、凭据、存储等核心能力不应因此任意开放。新增自有业务可以用 `extension:*` 与插件 RPC，缺的是统一 UI 贡献和完整的宿主集成契约。

其他已核对限制：

- 多能力插件的默认选择按整组管理：选中另一个实现或切回某个内置能力会清除原插件的整组默认选择。与当前文档一致，属于粒度偏粗的设计，不列为实现 bug。
- 后端先切换、前端加载失败保留旧视图是现行边界；不保证前后端作为一个原子版本一起发布。工具注册应绑定实际运行版本，兼容性仍需明确约定。
- SDK 的 `ServiceContract` 直接取宿主实现类的公开成员；组件接口也要求参照内置组件。独立作者依赖宿主内部演进，缺乏可冻结的服务/视图契约。
- 本次未验证所有服务的第三方完整替换、依赖环、强制终止第三方代码、任意平台兼容、所有浏览器展示及长时资源占用；没有将专项通过等同于“整个框架无缺陷”。

## 整改顺序与验收标准

1. **先补故障隔离和契约。** 修复 D1–D5，针对已复现触发条件建立正常行为的回归测试；明确契约版本与可选能力，修正插件详情的生效方式说明。
2. **补通用工具声明与承载。** 实现 `contributes.tools`、按插件作用域注册页面、通用左侧工具区和工作区标签。第一阶段仅开放 `sidebar.tools`，入口元数据、图标和组件受实际运行清单约束；不是任意 DOM 注入。
3. **迁移任务管理器作验证。** 去掉主页面的任务管理器专用按钮、标签和关闭分支；让它以同一公共 API 声明入口。保留服务替换兼容适配，运行连接与原有会话实例不被重建。配置同步、AI 设置再按实际核心边界逐项迁移。
4. **交付两个互不相关的独立工具示例。** 在同一宿主构建中，只安装插件文件就出现两个各自入口；新增第二个工具时宿主源码零修改；随后再实施系统优化。

验收不能止于“能出现一个按钮”。必须覆盖安装后出现入口、禁用/卸载后撤销入口、当前页关闭与资源回收、等待任务期间显示实际运行状态、版本更新失败保留旧页、重复注册/未知位置/无效图标阻断、迟到异步注册无效、多页面同步以及原有 SSH/桌面会话不重建。布局仍保持左侧导航、顶部搜索/标签/设置与右侧内容区。
